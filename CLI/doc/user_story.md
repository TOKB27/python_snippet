# ユーザーストーリー一覧（systemA CLI）

## 1. 背景

本ドキュメントは、ADRで定義された「安全な認証」「API経由でのデータ取得」「使いやすいCLI体験」を実現するためのユーザーストーリーを整理したものです。
対象人物は「利用者」と「開発者」に絞り、CLIツール `systemA` を通じて認証、データ取得、結果確認をスムーズに行えることを目的とします。

なお、Pythonで構築する理由は、既存のバックエンド実装との整合性、型安全な開発、CLI開発の効率性が高く、他の自動化ツールやジョブとの連携がしやすいためです。

---

## 2. 用語の意味と粒度

本ドキュメントでは、以下の3つを明確に分けて扱います。

- Epic: 取り組む大きなテーマ。何を実現したいかを示す。
- User Story (US): そのテーマの中で、特定の利用者が得たい価値を表す。誰が、何を、なぜ必要かを示す。
- 受入基準: そのUSが完了したと判断できる具体的な条件。実装者と受け手が同じ判定基準で確認するための証拠。

つまり、

- Epic = 「大きな目的」
- US = 「利用者の価値」
- 受入基準 = 「完了の条件」

を意味します。

## 4. ユーザーストーリー

### Epic 1: systemAの情報を他ツールや自動化フローに組み込みたい

#### US-01

- 利用者として、`systemA` の取得データを簡単に自分の業務フローや他ツールに自然に取り込みたい
- そうすることで、手動操作の手間を削減し、データ連携の効率を高めたい

受入基準:

- 取得したデータをJSONや標準出力形式で簡単に他ツールへ渡せる
- 自動化スクリプトやジョブから一貫して利用できる
- 取得結果が人手で読むだけでなく、他システムとの連携に使える形式で返る

#### US-02

- 利用者として、`systemA` を安全に認証し、他のツールや自動化フローから利用できる状態にしたい
- そうすることで、データを手で転記したりすることなく、システム連携を自動化できる

受入基準:

- CLIを実行すると安全な認証フローが開始される
- 認証後に取得したトークンが、再利用できる状態で保持される
- 認証後に取得したトークンはローカルファイルへの平文保存が行われず、OSの安全な保管領域に保存される

### Epic 2: 必要なデータの取得、更新を迅速に実行したい

#### US-03

- 利用者として、GUIからの操作だと時間がかかる作業を自動化したい
- そうすることで、手作業での操作を減らし、複数のデータ取得と更新を効率よく進められる

受入基準:

- CLI実行時に保存済みの認証情報を自動で利用する
- GUIでの手作業操作より短時間でデータ取得や更新フローを進められる
- 認証失敗時や期限切れ時に明確な案内が表示される

#### US-04

- 利用者として、認証状態が不十分なときに分かりやすく通知されたい
- そうすることで、どの操作をすべきか迷わずに次の行動に進める

受入基準:

- トークンがない場合、認証を促すメッセージが表示される
- トークンが期限切れの場合、再認証が必要であることが明示される
- エラーメッセージが簡潔で、次の一手がわかる

### Epic 3: 使いやすく、導入しやすいツールを使いたい

#### US-05

- 利用者として、GitHub CLIのような自然な操作感を持つツールを使いたい
- そうすることで、学習コストが低く、すぐに使い始められる

受入基準:

- コマンドやオプションが直感的で理解しやすい
- 処理中の状態が分かる表示がある
- 使い慣れた開発者でも、短時間で操作に慣れることができる

#### US-06

- 開発者として、ツールを簡単に配布・導入したい
- そうすることで、利用開始までの手間を減らし、導入のハードルを下げたい

受入基準:

- 単一の実行ファイルとして配布可能である
- 利用者がパッケージの個別インストールが不要である

### Epic 4: 安心して継続利用できるツールにしたい

#### US-07

- 開発者として、バックエンドと同じ言語で開発できるツールを使いたい
- そうすることで、保守性と知識の再利用性が高くなる

受入基準:

- CLI実装がPythonベースで統一されている
- 型情報や検証が取り入れられている
- バックエンド側の知見と開発者ツールの実装を共有しやすい

#### US-08

- 開発者として、認証・API接続・表示処理を分離した構成にしたい
- そうすることで、テストや改修がしやすくなり、長く運用しやすい

受入基準:

- 認証処理、API呼び出し、表示処理が分離されている
- テストが行いやすい構造になっている
- 将来のコマンド追加や機能拡張がしやすい

## 4. 非機能要件

### セキュリティ

- 認証トークンはローカルファイルではなくOSネイティブの安全な保管領域に保存する
- API Gateway の認証機構により、未認証アクセスを防ぐ

### 使いやすさ

- 実行コマンドが短く、自然な操作である
- エラー時に、次に取るべき行動が明確に示される
- CLIの出力がターミナルで読みやすい形式である

### 保守性

- Python + Typer + Rich による一貫した実装を採用する
- 型安全性とコード整形を維持し、レビューしやすい構造にする
- 既存のAWS基盤と整合した設計にする

### 配布性

- 生成物を単一実行ファイルとして配布できるようにする
- 導入時の依存環境を最小限に抑える

---

## 5. まとめ

本ユーザーストーリーは、ADRで示された「安全な認証」「API経由のデータ取得」「使いやすいCLI体験」「継続利用しやすさ」を、利用者の視点で整理したものです。
`systemA` は、セキュリティと使いやすさを両立しながら、開発者や運用担当者が短時間で業務を進められるツールとして設計されるべきです。

> 重要な整理: Epic は大きな目的、US は利用者の価値、受入基準は完了条件を表します。  
> そのため、Epic と US は「何を目指すか」を示し、受入基準は「それが達成されたかどうか」を確認するための基準です。
